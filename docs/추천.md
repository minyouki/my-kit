# 추천 — 기술 스택과 작업 순서

> planner와 PLAN을 확정할 때 참고하는 기준 문서. 여기 적힌 스택·순서는 제안이며, 과제에 맞게 조정해 PLAN에서 확정한다.

## 1. 추천 기술 스택

### A. 경량형 (기본 추천)

| 영역 | 선택 |
| ---- | ---- |
| 프론트 | 정적 HTML + 바닐라 JS (또는 Alpine.js) |
| 백엔드 | FastAPI(Python) 또는 Express(Node). 같은 서버가 정적 파일 서빙 |
| DB | SQLite |

- **적합한 상황:** 화면 4개 이하, 폼·목록·간단한 대시보드, 상태가 단순함
- **장점:** 빌드 단계 없음, 실행 명령 하나, 샌드박스 실행 실패 위험 낮음
- **단점:** 상태가 많은 화면은 코드가 길어짐

### B. 컴포넌트형

| 영역 | 선택 |
| ---- | ---- |
| 프론트 | React + Vite (스타일은 Tailwind) |
| 백엔드 | FastAPI 또는 Express (API 전용) |
| DB | SQLite 또는 PostgreSQL |

- **적합한 상황:** 드래그앤드롭, 실시간 갱신 등 상호작용·상태가 많은 화면
- **장점:** 컴포넌트 재사용, AI가 학습한 예제가 많음
- **단점:** 설정·빌드 시간이 들고 프론트/백엔드를 따로 띄워야 함

**선택 기준:** 기본은 A. 상호작용이 많을 때만 B. 익숙한 언어가 있으면 그쪽을 우선한다. 핵심 로직이 알고리즘·데이터 처리 중심이면 백엔드 언어를 그쪽에 강한 것(Python 등)으로 정한다.

## 2. 권장 작업 순서

이 순서를 참고해 PLAN의 작업(T)과 순서를 확정한다. 과제 이해·담당자 질문 결과에 맞게 단계를 더하거나 줄인다.

원칙: 계약(API+스키마)을 먼저 정하고, 기능 하나를 DB → API → 화면까지 끝낸 뒤 다음으로 간다. 매 단계 직접 실행해 확인한다.

| 순서 | 단계 | 할 일 |
| ---- | ---- | ----- |
| 1 | 기획 | 핵심 시나리오 1~2개, 필수/선택 구분, 데이터 모델(표 3~5개) |
| 2 | 계약 정의 | API 목록(경로·요청·응답)과 DB 스키마 확정 |
| 3 | 디자인 | 화면 3~4개 목록, 색·글꼴·간격 토큰만 정함 |
| 4 | 뼈대 | 프로젝트 생성, 환경변수, 헬스체크, 빈 화면 실행 |
| 5 | 기능 구현 | 시나리오 순서대로 기능별 수직 슬라이스 (DB → API → 화면) |
| 6 | 검증·에러 처리 | 빈 입력, 잘못된 값, API 실패, 새로고침 후 유지, 화면 캡처 |
| 7 | 정리 | 실행 방법 문서, 환경변수 예시, 불필요한 코드 제거 |

### 지킬 점

- 인증·배포는 뼈대만 만들고 뒤로 미룬다.
- 디자인 시스템·라이브러리를 새로 고르는 데 시간을 쓰지 않는다.
- AI에게는 기능 단위로 시키고 한 번에 하나씩 검증한다.
- 에러 처리·빈 상태·새로고침 후 유지를 마지막까지 미루지 않는다.
